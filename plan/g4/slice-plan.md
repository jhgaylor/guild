# G4 Slice Plan

**Generated:** 2026-05-26  
**Source:** plan/g4-framing/framing.md  
**Gate:** Driver reviews and approves this plan before any slice is dispatched.

G4 hardens the platform surfaced by G3: correctness (race), security (auth, secrets), durability (retries), extensibility (adapters), and scale (multi-worker). Eight framing items mapped to six slices in priority order.

## Slice 1 — Race Fix, UI Auth, SECRET_KEY_BASE

**Goal:** Close the three highest-severity correctness/security gaps with no architectural decisions required.

### In-scope

- `lib/guild/claiming.ex` — wrap claim attempt in `Repo.transaction/1` with `Ecto.Adapters.SQL.query!/3` advisory lock (`pg_try_advisory_xact_lock(thread_id)`) so concurrent webhooks for the same issue serialize; second caller gets `{:error, :already_claimed}` and no-ops.
- `lib/guild_web/router.ex` — add `:auth` pipeline using `Plug.BasicAuth` in front of all browser routes (`/threads`, `/threads/:id`, `/decisions`). Credentials read from `OPERATOR_USERNAME` / `OPERATOR_PASSWORD` env vars.
- `lib/guild_web/endpoint.ex` — remove inline `secret_key_base: "…"` literal; replace with `System.fetch_env!("SECRET_KEY_BASE")`.
- `k8s/secret.yaml` — add `SECRET_KEY_BASE`, `OPERATOR_USERNAME`, `OPERATOR_PASSWORD` keys (placeholder base64 values with operator comment).
- `test/guild/claiming_test.exs` — concurrent claim test: spawn two tasks claiming the same issue simultaneously, assert exactly one `:ok` and one `{:error, :already_claimed}`.
- `test/guild_web/controllers/thread_controller_test.exs` — assert unauthenticated GET /threads returns 401.

### Stubbed at this slice

- Role-based access control (single set of credentials is enough).
- Rate limiting on the basic auth endpoint.

### ADRs required

None.

### Acceptance criteria

- `mix test --exclude e2e` green.
- Two concurrent `claim_issue` calls for the same issue → exactly one Fountain dispatch.
- GET /threads without credentials → 401.
- `SECRET_KEY_BASE` absent at startup → `System.fetch_env!/1` raises (fail-fast).

### Depends on

G3 main (PR #20–#23 merged).

### Estimate

~150 LOC + tests. One engineer, one reviewer pass.

## Slice 2 — Durable Claim Queue

**Goal:** Survive webhook handler crashes without losing work; replace `Task.start` fire-and-forget with a retryable job.

### In-scope

- ADR `decisions/0010-durable-claim-queue.md` — choose between Oban, Broadway, and hand-rolled `claim_jobs` Postgres table. Recommend Oban unless constraints rule it out.
- `mix.exs` — add chosen library dependency.
- `lib/guild/workers/claim_worker.ex` (Oban path) — `perform/1` calls `Guild.Claiming.claim_issue/2`; on `{:error, :already_claimed}` returns `{:cancel, :already_claimed}`; on transient errors returns `{:error, reason}` for Oban retry.
- `lib/guild_web/controllers/webhook_controller.ex` — replace `Task.start(fn -> maybe_claim_from_event(…) end)` with job enqueue (e.g. `ClaimWorker.new(%{…}) |> Oban.insert!()`).
- `lib/guild/application.ex` — add Oban supervisor (if Oban chosen).
- `priv/repo/migrations/TIMESTAMP_add_oban_jobs.exs` — Oban schema migration (generated by `mix oban.install`).
- `test/guild/workers/claim_worker_test.exs` — assert job performs claim; assert already-claimed cancels cleanly; assert transient error returns `{:error, _}`.

### Stubbed at this slice

- Dead-letter queue / alerting on exhausted retries.
- Job UI (Oban Web).

### ADRs required

- `decisions/0010-durable-claim-queue.md` — must be written and committed before implementation begins.

### Acceptance criteria

- Webhook handler returns 200 immediately; claim runs in job worker.
- Killing the app mid-claim and restarting retries the job.
- `mix test --exclude e2e` green.

### Depends on

Slice 1 merged.

### Estimate

ADR (~1 page) + ~80 LOC implementation + tests. One engineer.

## Slice 3 — Decisions Log Retention + Context Summarization *(may defer to G5)*

**Goal:** Fulfil the two outstanding ADR TODOs (ADR 0009 retention policy, ADR 0007 summarization) so long-running threads don't bloat unboundedly.

### In-scope

- `decisions/0009-decisions-log-retention.md` — update with chosen retention policy (e.g. keep last N decisions per thread, archive older rows to a `decisions_log_archive` table or delete).
- `lib/guild/retention.ex` — `Guild.Retention` module; `trim_decisions_log/1` trims per-thread rows beyond the limit; called from `Guild.Reconcile` after Pass B (thread :done).
- `decisions/0007-context-summarization.md` — update with summarization trigger (e.g. context_notes count > threshold) and approach (Fountain conv summarizer agent or inline LLM call via Fountain API).
- `lib/guild/summarization.ex` — `Guild.Summarization.maybe_summarize/1`; checks context_notes count against threshold; if over, calls Fountain to produce a summary, writes a new `ContextNote` with `note_type: :summary`, marks old notes `:archived`.
- `lib/guild/reconcile.ex` — hook `Retention.trim_decisions_log/1` and `Summarization.maybe_summarize/1` into reconcile loop.
- Tests for both modules (unit, with sandbox).

### Stubbed at this slice

- UI for archived decisions / notes.
- Configurable retention limits via runtime env (hardcode constants for now).

### ADRs required

- Update `decisions/0009-decisions-log-retention.md`
- Update `decisions/0007-context-summarization.md`

### Acceptance criteria

- `mix test --exclude e2e` green.
- Thread with > N decisions after :done has trailing rows trimmed.
- Thread with > threshold context_notes triggers summarization; summary ContextNote written; old notes archived.

### Depends on

Slice 2 merged. **May defer to G5** if adapter work (Slices 4–5) is higher operator priority.

### Estimate

ADR updates + ~150 LOC + tests. One engineer.

## Slice 4 — Slack Adapter

**Goal:** Enable Guild to post thread status updates and decision summaries to a Slack channel, replacing the `:not_configured` stub.

### In-scope

- `lib/guild/adapters/slack.ex` — `Guild.Adapters.Slack`; replace `:not_configured` stub; implement `post_message/2` via Slack Web API (`chat.postMessage`); reads `SLACK_BOT_TOKEN` + `SLACK_CHANNEL_ID` from env; graceful no-op if vars absent.
- `lib/guild/reconcile.ex` — call `Slack.post_message/2` on `:pr_open` and `:done` state transitions with a templated message (thread anchor, PR link if applicable).
- `k8s/secret.yaml` — add `SLACK_BOT_TOKEN`, `SLACK_CHANNEL_ID` keys.
- `test/guild/adapters/slack_test.exs` — bypass/mock HTTP; assert correct payload shape; assert graceful no-op when env absent.

### Stubbed at this slice

- Interactive Slack actions (approve/reject from Slack).
- Per-repo Slack channel routing.
- Thread-per-issue Slack threads (single channel message only).

### ADRs required

None.

### Acceptance criteria

- `mix test --exclude e2e` green.
- With `SLACK_BOT_TOKEN` and `SLACK_CHANNEL_ID` set: reconcile :done posts a Slack message.
- Without env vars: no crash, no message.

### Depends on

Slice 1 merged. (Can run in parallel with Slices 2–3.)

### Estimate

~200 LOC + tests. One engineer.

## Slice 5 — Linear Adapter

### In-scope

- `lib/guild/reconcile.ex` — create Linear issue on thread `:claimed`; update to "In Progress" on `:executing`; update to "Done" on `:done`.
- `k8s/secret.yaml` — add `LINEAR_API_KEY`, `LINEAR_TEAM_ID` keys.
- `test/guild/adapters/linear_test.exs` — bypass/mock HTTP; assert GraphQL payload shape; assert graceful no-op when env absent.

### Stubbed at this slice

- Custom Linear workflow states per team.

### ADRs required

None.

### Acceptance criteria

- `mix test --exclude e2e` green.
- With credentials set: thread `:claimed` → Linear issue created; `:done` → Linear issue marked Done.
- Without env vars: no crash.

### Depends on

Slice 1 merged. (Can run in parallel with Slices 2–4.)

### Estimate

~200 LOC + tests. One engineer.

## Slice 6 — Multi-Worker + Multi-Repo

**Goal:** Allow multiple Guild worker agents and multiple monitored repos to operate without claiming conflicts or credential collisions.

### In-scope

- `decisions/0011-claiming-arbitration.md` — design for distributed claim arbitration (e.g. Postgres advisory locks per repo+issue, or a central claim coordinator GenServer behind a distributed registry).
- `decisions/0012-per-worker-credentials.md` — design for scoping `vault_id` / `FOUNTAIN_API_KEY` per worker identity rather than a single global credential set.
- `decisions/0013-multi-repo-deployment.md` — design for deployment topology: one Guild instance per repo vs. a single instance with repo routing config.
- Implementation per chosen designs (expected ~400+ LOC, may split into sub-slices 6a/6b after ADRs are written).
- Schema migrations for any new tables (e.g. `workers`, `repos` config tables).
- Updated k8s manifests if multi-instance topology chosen.

### Stubbed at this slice

- UI for managing workers/repos.
- Cross-repo dependency tracking.

### ADRs required

- `decisions/0011-claiming-arbitration.md` (new)
- `decisions/0012-per-worker-credentials.md` (new)
- `decisions/0013-multi-repo-deployment.md` (new)

**All three ADRs must be written and operator-approved before implementation begins. Slice 6 should be split into 6a (ADRs + schema) and 6b (implementation) once designs are settled.**

### Acceptance criteria

- Two Guild workers targeting the same repo do not double-claim the same issue.
- Each worker uses its own vault_id / credentials.
- `mix test --exclude e2e` green.
- Chosen deployment topology documented and applied to k8s manifests.

### Depends on

Slices 1–5 merged (or operator decision to parallelize).

### Estimate

ADRs (~3 pages total) + 400+ LOC. Likely 2 sub-slices. Biggest design lift in G4.
